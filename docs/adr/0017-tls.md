# ADR 0017 — TLS pela API do sistema, negociado dentro do protocolo

**Data:** 2026-09-21
**Status:** Aceito

## Contexto

Os dois drivers falavam em claro. Isso custava três coisas:

1. Qualquer conexão remota trafegava senha e dados sem criptografia.
2. O `caching_sha2_password` do MySQL 8 — que é o padrão dele — precisava do
   caminho RSA para a primeira autenticação de cada conta. Sobre TLS, o
   protocolo manda a senha em claro dentro do canal cifrado, sem chave pública.
3. O `mysql_clear_password`, que é como PAM e LDAP funcionam, era recusado —
   corretamente, porque sem TLS ele expõe a senha.

A aba SSL do diálogo de conexão existia com os campos, e dizia na tela que não
estava implementada (diretiva 6).

## Decisão

**TLS pela API de TLS do sistema operacional: Schannel no Windows, OpenSSL no
Linux.** Sem biblioteca de terceiros vendorizada.

**O canal envolve um socket já conectado**, em vez de conectar por dentro.

**Modos com os nomes do `sslmode` do PostgreSQL**, que o DBeaver também usa:
`disable`, `allow`, `prefer`, `require`, `verify-ca`, `verify-full`.

## Justificativa

### Por que a API do sistema

Vendorizar OpenSSL traria ~500 mil linhas de C para dentro do link estático, e
com elas a responsabilidade de acompanhar cada CVE. A API do sistema herda as
atualizações de certificado e de cifra pelo Windows Update ou pelo gerenciador
de pacotes — que é onde essa manutenção já acontece de qualquer forma.

O custo é uma implementação por plataforma. Foi aceito porque as duas são
pequenas (~450 linhas cada) e o `crypto_win32.cpp`/`crypto_openssl.cpp` já
tinham estabelecido esse mesmo par.

### Por que envolver um socket já aberto

Os dois protocolos de banco **negociam o TLS dentro da própria conversa**:

- PostgreSQL manda um `SSLRequest` (mensagem sem byte de tipo, com o código
  mágico 80877103) e lê **um byte** de resposta — `S` aceita, `N` recusa —
  antes do aperto de mão.
- MySQL lê o `HandshakeV10` do servidor **em claro**, responde com um
  `HandshakeResponse41` truncado (só os 32 bytes de cabeçalho, sem usuário nem
  senha) marcando `CLIENT_SSL`, e só então inicia o TLS. O `sequence_` do
  pacote **não reinicia**.

Em nenhum dos dois o TLS começa no primeiro byte da conexão. Um
`TlsSocket::connect(host, port)` não serviria para nenhum deles.

### Por que `allow` e `prefer` não exigem TLS

No libpq eles significam "tenta cifrar, aceita em claro". Isso protege contra
um escuta passivo e contra mais ninguém. São aceitos no perfil, para não perder
o valor de uma conexão importada do DBeaver, mas **não exigem** — e a aba SSL
diz isso na tela quando um deles é escolhido. Tratá-los como garantia seria
mentir para o usuário; recusá-los quebraria perfis que o DBeaver aceita.

### Por que `require` não verifica o certificado

Porque é onde ele mais aparece: servidor de desenvolvimento com certificado
autoassinado. Um `require` que validasse a cadeia seria indistinguível de
`verify-ca`, e a escolha entre os dois deixaria de existir.

## O que foi rejeitado

**Vendorizar OpenSSL ou mbedTLS.** Traz a superfície de CVE para dentro do
nosso ciclo de release. Rejeitado pelo mesmo raciocínio do ADR 0009.

**Um booleano `use_tls` em vez de modos.** Não distingue "cifrar" de "cifrar e
verificar", que são decisões diferentes com consequências diferentes. Um
booleano forçaria escolher um dos dois como padrão implícito.

**Guardar um `Socket*` dentro do `TlsChannel`.** Foi a primeira versão, e
estava errada: a `Connection` que contém os dois é **movida** para dentro do
`Holt` depois de conectar, o socket muda de endereço, e o ponteiro passa a
apontar para o objeto esvaziado. O sintoma foi "An operation was attempted on
something that is not a socket" na primeira consulta — **depois** de um aperto
de mão bem-sucedido. O socket agora vai em cada chamada.

## Consequências

- `mysql_clear_password` passa a ser aceito **sob TLS**, e só sob TLS.
- `caching_sha2_password` sobre TLS manda a senha em claro no canal, sem RSA.
- A barra de status mostra um cadeado com o protocolo e a cifra negociados
  ("TLS 1.2, TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384"). Não há símbolo para "em
  claro": a ausência do cadeado é a informação, desde que ele nunca minta
  quando aparece.
- Certificados de cliente são **gravados e lidos** — um perfil importado do
  DBeaver não os perde — mas ainda não são usados no aperto de mão. A aba SSL
  diz isso.
- No Linux `tls_available()` responde `false`, e a caixa "usar SSL" aparece
  desligada com o aviso — em vez de falhar na hora de conectar.

## Verificação

`spikes/dbeaver_import/tls_live.cpp`, contra o MySQL local:

- sem TLS conecta e reporta canal em claro;
- `require` negocia TLS 1.2 e a consulta roda **depois** do upgrade;
- `verify-full` recusa o certificado autoassinado.

A terceira é a que mais importa: se passasse, a verificação não estaria
acontecendo, e o modo seria um rótulo sem efeito.

O caminho do PostgreSQL compila e segue o protocolo, mas **não foi verificado
contra servidor** — não há perfil PostgreSQL local com senha salva.
